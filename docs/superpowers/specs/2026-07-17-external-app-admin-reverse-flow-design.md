## 2. 背景

现有配置后台主要表达从商品供给到发布、交易和权益生效的正向流程。仓库虽然已经定义了审批驳回、暂停销售、下架、退款、权益过期、席位收回、空间回调延迟、需求回流和求上架等状态，但这些动作分散在不同模块，尚未形成跨系统、可追踪、以客户处置完成为终点的逆流程。

典型问题包括：

- 暂停销售只改变商品状态，没有统一识别在途订单、已购客户和有效权益。
- 退款与权益回收缺少一致的先后关系，容易出现已退款仍可使用或退款失败但权益已删除。
- 空间回调延迟只展示告警，没有形成自动对账、人工修正和关闭证据。
- 需求线索可以被标记为推荐现有、需要定制或暂不支持，但没有继续关联商品立项、加工、发布和客户回告。
- 热门词、推荐位、AI 引导问题和价格等运营配置缺少版本发布与回滚机制。
- 各模块能够完成自己的动作，但缺少对客户通知、补偿、跨系统一致性和审计结果负责的统一载体。

## 3. 目标与非目标

### 3.1 目标

- 建立“需求回流闭环”和“履约补偿闭环”两类逆流程。
- 保留各业务模块的操作入口，并用统一逆向工单串联跨模块、跨系统及客户处置任务。
- 分离销售、服务、交付、权益和审批状态，避免单一状态误伤存量客户。
- 为暂停、下架、召回、退款、合同终止、交付异常、权益回收、配置回滚和需求重开定义明确规则。
- 将影响分析、止损、客户通知、补偿、对账和审计纳入工单关闭门槛。
- 保证所有历史订单、权益、审批、配置版本和人工修正记录可追溯。

### 3.2 非目标

- 不在本设计中实现真实支付、财务退款、合同解约、法务审批或可信空间接口。
- 不展开支付、财务、法务等外围系统内部流程，仅定义触发条件、责任人、所需回传状态和异常处理。
- 不重做 PC 运营后台全部信息架构；第一阶段不新增一级菜单。
- 不把所有本地可恢复的小错误都升级为人工工单。
- 不使用逆向流程替代正常的商品发布、订单履约、权益发放和需求处理流程。

## 4. 核心原则

1. **停止新购不等于停止存量服务。** 暂停销售只控制新交易，存量权益依据暂停原因和授权规则单独处理。
2. **状态分轴。** 销售、服务、交付、权益和审批状态分别记录，不通过一个商品状态推导全部行为。
3. **原模块发起，统一工单收口。** 业务动作仍在商品、商业化、权益、线索等模块发起；跨系统或影响客户时自动创建逆向工单。
4. **先止损，再处置。** 紧急合规或安全事件可以先冻结能力，再补充审批和影响分析，但必须保留紧急操作记录。
5. **退款成功后再撤销权益。** 退款申请阶段默认冻结权益；退款失败或驳回后恢复，除非另有独立的合规冻结原因。
6. **空间事实以空间侧为准。** 可信空间订单和交付结果以空间侧权威状态为准，APP 通过回调与主动查询完成对账。
7. **不物理删除业务历史。** 订单、权益、审批、需求、配置版本、通知和人工修正均保留时间线。
8. **客户处置完成才算闭环。** 后台接口或按钮执行成功不能作为逆向工单关闭依据。
9. **原因驱动处置。** 商业调整、质量故障、合规风险、上游停供和配置错误采用不同的存量客户策略。
10. **重复执行必须幂等。** 自动重试、重复回调和人工补发不得产生重复订单、权益、退款或通知。

## 5. 总体架构

### 5.1 业务双闭环

需求回流闭环解决“市场需要什么”：

```text
搜索无结果／询价／求上架／试用反馈
→ 需求去重与聚合
→ 商品规划
→ 资产加工或内容生产
→ 合规与发布审批
→ 商品发布
→ 回告原需求客户
→ 观察使用与转化
```

履约补偿闭环解决“已发生业务如何撤销、修复或补偿”：

```text
异常／撤销／策略调整
→ 生成影响快照
→ 判断风险等级
→ 止损
→ 处理订单、交付和权益
→ 通知及补偿客户
→ 跨系统核对
→ 审计关闭
```

### 5.2 统一逆向工单触发条件

原业务模块完成以下动作时，满足任一条件即创建统一逆向工单：

- 影响已购客户、有效订单、在途交付、合同或存量权益。
- 需要两个及以上系统或业务模块协同。
- 涉及退款、补偿、合同、合规或安全判断。
- 自动执行在首次失败后重试 3 次仍未成功；具体连接器可以因风险降低次数，但不得未经审批提高次数。
- 不能在原模块内一次完成。
- 需要向客户发送通知或保留责任链路。

纯本地、无客户影响且能够原子完成的配置修改不创建逆向工单，但仍记录配置版本和操作审计。

### 5.3 后台承载

第一阶段在“审批与集成”下增加“逆向工单”子页，不新增一级菜单。商品中心、商业化中心、企业权益、试用与线索和运营配置保留原操作入口，并展示关联工单编号和处理进度。

未来只有在工单量、角色规模和运营复杂度显著增长后，才将该能力独立为“异常与售后中心”。

## 6. 状态模型

### 6.1 状态分轴

| 状态轴 | 状态 |
| --- | --- |
| 销售状态 | 草稿、在售、暂停销售、下架 |
| 服务状态 | 正常、降级、暂停服务、终止服务 |
| 交付状态 | 待交付、交付中、成功、失败、撤回 |
| 权益状态 | 待生效、有效、冻结、迁移中、到期、撤销 |
| 审批状态 | 待审批、通过、驳回、撤回、重新提交 |
| 退款状态 | 未申请、退款审核中、退款执行中、成功、失败、驳回 |

商品可以同时处于“暂停销售、服务正常、历史权益有效”。商品召回则通常进入“暂停销售、暂停服务、权益冻结”，并根据客户处置结果进入恢复、迁移、退款或撤销。

### 6.2 原因分类

逆向动作至少区分以下原因：

- 商业策略调整；
- 数据质量或服务故障；
- 合规或安全风险；
- 上游永久停止供给；
- 运营配置错误；
- 客户主动取消或退款；
- 支付或财务失败；
- 交付失败或回调异常；
- 企业身份、合同或认证不匹配。

原因决定止损范围、存量权益策略、通知模板、审批要求和补偿方式。

## 7. 需求回流闭环

### 7.1 来源

需求回流统一接收：

- 搜索无结果；
- 用户询价；
- 候选资产求上架；
- 试用反馈或商品不匹配；
- 已推荐商品仍不能满足需求；
- 商品暂停、下架后客户提出的替代需求。

### 7.2 处理流程

```text
客户需求
→ 去重与相似需求聚合
→ 价值、可行性、合规性评估
→ 推荐现有／关联准备中商品／商品立项／定制项目／暂不支持
→ 商品加工或项目交付
→ 发布或交付完成
→ 回告所有原始需求客户
→ 记录查看、试用、购买或放弃结果
```

### 7.3 数据边界

- 一条需求记录只代表一个客户诉求。
- 多条相似需求可以聚合到一个商品加工任务。
- 一个商品加工任务可以关联多个原始需求。
- 合并需求不删除原始记录，每个客户仍只能看到自己的需求、反馈和进度。
- 商品发布后关联商品 ID，并向所有相关需求生成独立通知任务。

### 7.4 逆向动作

需求和求上架流程支持：

- 用户在进入实质加工前撤回；
- 评估中补充资料；
- 重复需求合并；
- 聚合需求按不同场景拆分；
- “暂不支持”在数据、政策或供给条件变化后重新打开；
- 推荐商品不匹配时返回评估；
- 已上架商品后续暂停、下架或召回时重新进入客户处置。

客户撤回只关闭该客户的需求订阅和后续通知。如果该需求已经与其他客户共同形成商品加工任务，撤回单条需求不得自动取消共享加工任务；运营人员根据剩余需求重新评估任务价值。

## 8. 商品、审批与空间同步逆流程

### 8.1 暂停、下架和召回

| 动作 | 含义 | 新客户 | 已购客户默认原则 |
| --- | --- | --- | --- |
| 暂停销售 | 暂时禁止新购 | 禁止新购 | 默认继续履约，依据原因决定降级、冻结或补偿 |
| 下架 | 永久停止新购并退出普通目录 | 不可搜索和购买 | 能履约则按原授权继续；不能履约则迁移、退款或终止合同 |
| 商品召回 | 存在合规、安全或严重质量风险 | 立即禁止新购 | 冻结受影响能力，逐户执行整改、迁移、退款或终止 |

发起动作前生成影响预估，至少包括：

- 在途订单和交付；
- 已购个人及企业客户；
- 有效权益、剩余期限和已使用范围；
- 试用、空间交付和企业成员席位；
- 推荐位、搜索索引、AI 引用及内容关联；
- 合同、退款和客户通知影响。

紧急合规召回可以先止损，但必须立即创建 S1 工单并补充影响快照、审批及客户处置方案。

### 8.2 暂停原因与存量客户策略

| 原因 | 存量客户处理 |
| --- | --- |
| 商业策略调整 | 继续使用至权益到期，停止续购和新增购买 |
| 临时服务故障 | 保留权益，标记服务降级；恢复后延期或补发额度 |
| 数据质量问题 | 限制受影响能力，修复并验证后恢复；按影响时长补偿 |
| 合规或安全风险 | 立即冻结受影响能力，执行整改、替代商品、退款或合同终止 |
| 上游永久停供 | 转为下架，能履约则继续，否则迁移或按剩余期限退款 |

暂停必须设置复核时间和负责人，到期后选择恢复销售、继续暂停或转为下架，不能无限期无主停留。

### 8.3 审批逆流程

```text
待审批 → 申请人撤回 → 修改 → 重新提交
待审批 → 审批驳回 → 整改 → 重新提交
审批通过未发布 → 撤回发布
已发布 → 发现重大风险 → 紧急召回／重新审批
```

重新提交创建新审批版本，旧版本和审批意见不可覆盖。商品内容、价格、获取方式、授权范围或合规声明发生重大变化时必须重新审批；推荐语、排序权重等纯运营信息不触发商品合规重审，但仍走配置版本发布。

已发布商品的非风险重大变更以新版本提交审批，审批期间当前已发布版本继续服务；只有新版本审批通过并发布后才替换当前版本。发现合规、安全或严重质量风险时不得继续保留当前版本，必须先召回或冻结，再进入重新审批。

### 8.4 可信空间商品变更

```text
接收空间变更
→ 校验版本并生成字段差异
→ 判断交易和客户影响
→ 冻结冲突配置
→ 运营确认
→ 更新 APP 展示与购买入口
→ 处理存量订单、交付和权益
```

- 空间主数据变更不能直接覆盖 APP 展示增强信息。
- 同步失败或超时不能自动判定商品下架。
- 空间商品下架时立即停止新购，存量履约依据空间回传策略处理。
- 旧版本同步事件不得覆盖更新状态。

## 9. 订单、合同与交付逆流程

### 9.1 待支付订单

```text
待支付
→ 用户取消／超时／支付失败
→ 关闭支付入口
→ 释放优惠、额度或预占资源
→ 保留订单记录
→ 允许重新下单
```

没有有效支付的订单不创建权益，也不进入退款流程。支付结果不明确时进入“支付结果核对”，通过支付流水确认后再标记成功或关闭。

### 9.2 已支付但权益未到账

```text
支付成功
→ 权益创建失败
→ 幂等自动重试
→ 超过阈值创建逆向工单
→ 人工补发权益或退款
→ 通知客户
```

支付成功记录不能因权益发放失败回退为“未支付”。重复回调和人工补发必须使用业务幂等键，避免重复权益。

### 9.3 退款

```text
发起退款
→ 校验订单、合同和使用情况
→ 确认退款政策
→ 权益冻结
→ 退款审批
→ 支付／财务执行
→ 退款成功后撤销权益
→ 通知客户并对账关闭
```

- 退款失败或被驳回时恢复权益；若商品另有合规冻结，则继续保持该冻结。
- 服务方责任可以追加延期、额度、替代商品或其他补偿。
- 合规召回应支持批量主动退款，不要求客户逐一申请。
- 对不可逆的数据下载、API 调用或已交付版本，依据已使用范围和合同条款确定全额、部分或不退款。

### 9.4 企业合同终止

```text
发起合同终止
→ 核对生效日期与条款
→ 识别企业权益和成员席位
→ 停止续费与新增席位
→ 冻结或保留至终止日
→ 财务结算／退款
→ 到期撤销企业权益
→ 批量收回成员席位
→ 通知管理员和成员
```

单个成员退出企业只收回该成员席位，不影响企业套餐和其他成员。

### 9.5 可信空间订单异常

```text
空间受理
→ 回调延迟
→ APP 主动查询
→ 自动重试
→ 仍不一致则人工对账
→ 修正 APP 状态
→ 继续交付／补发权益／退款
```

回调延迟不等于购买失败，APP 不允许用户重复下单。对账结果包括：

- 空间成功、APP 未更新：补写订单和交付状态。
- 空间失败、APP 长期处理中：关闭订单并允许重试。
- 空间已扣款但交付失败：继续履约或发起退款。
- 企业身份不匹配：暂停交付并修正企业绑定。
- 商品已下架：停止新购，已有订单进入专项处置。

## 10. 权益、企业席位与补偿

### 10.1 权益逆向状态

```text
有效 → 冻结 → 恢复有效
有效 → 冻结 → 退款成功 → 撤销
有效 → 迁移中 → 替代权益生效 → 原权益撤销
有效 → 到期
```

权益状态变化追加时间线，不删除原权益。冻结必须记录原因、开始时间、预计复核时间和关联工单。

### 10.2 服务中断补偿

```text
发现中断
→ 计算影响范围和时长
→ 降级或冻结能力
→ 通知客户
→ 恢复服务
→ 延期／补发额度／迁移商品／退款
→ 客户处置核验
```

补偿通过独立记录表达，不篡改原始订单金额或原始权益期限。补偿类型包括延期、补发额度、替代商品权益、退款和合同减免。

### 10.3 企业权益

- 合同终止或企业套餐到期时，按生效时间统一撤销企业内容权益并收回关联席位。
- 席位被收回时只影响该成员，不改变企业套餐状态。
- 商品迁移时先授予替代商品权益，验证成员可用后再撤销原权益，避免迁移窗口内无服务。
- 企业管理员和受影响成员分别接收适合其角色的通知。

## 11. 试用与需求逆流程

### 11.1 试用

```text
待审批 → 用户撤回
待审批 → 运营驳回 → 补充资料后重提
已通过 → 风险冻结 → 恢复或终止
已通过 → 额度耗尽 → 追加额度或重新申请
已过期 → 重新申请
```

- 用户撤回与运营驳回使用不同原因码。
- 驳回必须说明是否允许重提。
- 合规风险、异常调用或企业认证失效可以冻结试用。
- 冻结不清零剩余额度，恢复后继续使用。
- 终止保留已使用额度和操作记录。
- 按最新商品规格，数据集不提供试用；API 只提供不调用真实服务的固定脱敏沙箱。

### 11.2 需求终态重开

“暂不支持”“已推荐”和“已关闭”不是不可恢复的物理终态。出现供给、政策、数据、客户场景或商品状态变化时，可以基于原需求创建“重新打开”事件，并保留之前的结论与反馈。

## 12. 运营配置回滚

### 12.1 版本化发布

热门词、推荐位、频道、AI 引导问题、会员价格等配置采用：

```text
编辑草稿
→ 影响预览
→ 审核或二次确认
→ 定时／立即发布
→ 运行监控
→ 回滚到指定历史版本
```

每次发布形成不可变版本，记录修改前后差异、修改人、审核人、生效范围、发布时间、关联商品、回滚目标和回滚原因。

价格、获取方式、会员范围、AI 来源约束等直接影响交易或内容安全的配置必须由另一名有权限人员审核；热门词、普通推荐位和非交易频道排序允许修改人二次确认后发布。批量影响 100 个及以上商品或全部用户入口的配置一律采用双人审核。

### 12.2 代表回滚规则

- 推荐商品暂停或下架：自动撤出推荐位并启用已配置候补商品。
- 热门词无结果：停止展示或切换到需求收集入口。
- AI 引导问题引用失效商品：切换为安全兜底问题，不生成无来源结论。
- 价格误配置：立即停止新购，锁定受影响订单，按订单时间决定原价履约、补差或退款。
- 频道配置错误：回滚上一版本，不删除错误版本及其影响记录。

配置回滚只恢复配置，不自动恢复已被暂停、下架或召回的商品。

## 13. 集成异常与人工修正

### 13.1 通用处理链

```text
接收事件
→ 校验签名和事件版本
→ 幂等处理
→ 首次失败后最多自动重试 3 次
→ 超过阈值进入异常队列
→ 创建逆向工单
→ 人工修复或重新执行
→ 跨系统对账
→ 关闭告警
```

系统必须防止旧事件覆盖新状态、重复回调产生重复业务对象、同步超时误判下架、人工修复被后续旧任务覆盖，以及 APP 与空间长期状态不一致。

人工修正必须填写原因，记录修改前后状态、操作者、时间和关联工单。修正后写入高于旧自动事件的处理版本，避免被再次覆盖。

## 14. 客户通知

影响客户的逆向动作生成统一通知任务：

- 操作前：计划暂停、合同到期、服务迁移。
- 操作中：权益冻结、交付延迟、退款处理中。
- 操作后：服务恢复、退款成功、权益迁移、商品重新上架。
- 发送失败：自动重试后转人工联系。

同一事件合并商品、订单和权益通知，避免多个模块重复发送。通知只展示客户需要理解的原因、影响、时间、处置结果和恢复入口，不暴露内部风控规则、审批细节或其他客户信息。

## 15. 统一逆向工单设计

### 15.1 工单类型

- 需求供给回流；
- 商品暂停、下架或召回；
- 审批撤回或整改；
- 订单取消或退款；
- 合同终止；
- 交付恢复或撤回；
- 权益冻结、迁移或补偿；
- 试用终止；
- 配置回滚；
- 集成对账和人工修正。

### 15.2 生命周期

```text
待评估
→ 影响分析
→ 处置方案确认
→ 执行中
→ 客户处理
→ 跨系统核验
→ 已关闭
```

处置方案被驳回时返回“影响分析”；执行任务失败时停留“执行中”并升级负责人；客户通知或补偿未完成时不能进入跨系统核验。

只有重复工单、误触发且尚未执行任何止损或客户动作的工单可以从“待评估”进入“已取消”，并记录取消原因和确认人。工单进入影响分析后不得直接取消，必须完成处置并关闭。已关闭工单发现新影响时不修改原工单，而是创建关联的后续工单。

### 15.3 分级与时限

| 等级 | 场景 | 默认要求 |
| --- | --- | --- |
| S1 紧急 | 合规安全风险、批量权益异常、严重数据泄露风险 | 立即自动止损，15 分钟内接单，1 小时内形成处置方案 |
| S2 高 | 已付未交付、批量回调异常、合同终止、影响多个客户 | 2 小时内接单，1 个工作日内形成解决方案 |
| S3 一般 | 单客户退款、普通配置回滚、试用异常 | 1 个工作日内接单，3 个工作日内关闭或给出明确计划 |

系统根据合规风险、影响客户数、有效订单数和金额给出建议等级。负责人可以调高；调低必须填写理由并由上一级负责人确认。

### 15.4 责任角色

- 发起人：在原业务模块发起动作。
- 工单负责人：对端到端闭环负责。
- 商品运营：处理商品、展示、推荐和替代商品。
- 合规审批人：处理召回、数据风险和重新审批。
- 商务/财务：处理合同、退款和补偿确认。
- 客户运营：负责通知、解释和客户确认。
- 系统执行器：执行同步、重试、冻结、补发和状态回写。
- 审计查看人：查看时间线，不修改业务结果。

同一 S1/S2 工单不能由发起人独自审批并关闭。

### 15.5 页面结构

“审批与集成—逆向工单”包括：

- 工单列表：等级、类型、来源模块、影响客户、负责人、时限和状态。
- 影响快照：商品、订单、合同、权益、成员、试用和需求。
- 处置方案：继续履约、冻结、迁移、退款、补偿、恢复或终止。
- 执行任务：按系统和责任角色拆分。
- 客户通知：对象、模板、渠道和送达结果。
- 对账结果：APP、资产平台、可信空间及支付/财务状态。
- 审计时间线：审批、修改、重试、回滚和人工修正。

## 16. 数据对象

| 对象 | 职责 |
| --- | --- |
| `ReverseWorkOrder` | 统一逆向工单、等级、类型、负责人、时限和状态 |
| `ImpactSnapshot` | 发起时及处置前的客户和业务影响快照 |
| `TreatmentPlan` | 止损、继续履约、冻结、退款、迁移、补偿或恢复方案 |
| `ExecutionTask` | 分派给业务模块、系统和角色的执行任务 |
| `CustomerNotice` | 通知对象、内容版本、渠道、发送和送达状态 |
| `CompensationRecord` | 退款、延期、额度、替代权益和合同减免记录 |

`ImpactSnapshot`、配置版本和审计时间线不可覆盖。业务当前状态可以更新，但每次人工修改都必须追加变更记录。

## 17. 工单关闭门槛

逆向工单只有同时满足以下条件才能关闭：

- 所有受影响客户、订单、合同和权益均已识别。
- 新购、调用、交付或数据风险已经停止。
- APP、可信空间及相关系统状态一致。
- 订单、退款、合同、交付和权益结果相互匹配。
- 客户通知已送达；失败通知已转人工并记录结果。
- 补偿、迁移、退款或恢复已经完成。
- 审批和执行证据完整。
- 已记录根因、改进动作、责任人和复发预防措施。

任何子任务、接口或后台按钮的单独成功都不能绕过上述门槛。

## 18. 运营指标

运营概览增加：

- 待处理逆向工单数；
- S1/S2 超时工单数；
- 受影响客户数；
- 退款和补偿金额；
- 自动恢复成功率；
- 平均恢复时间；
- 配置回滚次数；
- 重复异常率；
- 需求转商品率；
- 商品发布后的需求回告与购买转化率。

指标用于识别系统性问题，不能替代单个客户处置和工单证据。

## 19. 异常与恢复

- 影响快照生成失败：紧急事件先执行最小止损，禁止进入正式处置和关闭阶段，直至快照补齐。
- 自动任务部分成功：保留成功结果，仅重试失败任务，禁止全量重复执行。
- 客户通知失败：自动重试后转人工联系，不阻断必要止损，但阻断工单关闭。
- 退款失败：恢复权益或保持独立风险冻结，并向客户说明状态。
- 替代权益发放失败：保留原权益，除非合规风险要求继续冻结。
- 跨系统无法对账：工单升级到 S2；涉及合规或批量权益时升级到 S1。
- 配置回滚失败：停止继续发布，恢复最近一个已验证版本并创建人工修正任务。
- 负责人离岗或超时：自动升级到上一级负责人，不改变工单业务状态。

## 20. 验收场景

1. 商业原因暂停销售后禁止新购，历史客户继续使用至权益到期。
2. 合规原因召回商品后批量冻结受影响能力，并逐户完成退款、迁移或合同处置。
3. 已支付但权益未到账时自动重试，超过阈值后人工补发且不产生重复权益。
4. 退款失败或驳回后恢复权益；独立合规冻结不随退款失败解除。
5. 空间回调延迟时主动对账，不允许用户重复下单，并按空间权威结果修正 APP 状态。
6. 企业合同终止后按生效日撤销企业权益、收回成员席位并完成双层通知。
7. 多条求上架需求聚合为一个商品加工任务，商品发布后逐户回告并记录转化。
8. 价格配置错误时回滚配置，识别错误时间窗口内的订单并按政策处置。
9. 商品暂停、下架或召回后同步撤出推荐位、搜索索引和 AI 引用。
10. 运营配置可以回滚到指定历史版本，且错误版本和影响记录仍可查询。
11. 逆向工单所有执行任务完成但客户通知失败时不能关闭。
12. 人工修正空间订单后，旧回调不能覆盖修正结果。

## 21. 实施边界建议

第一阶段优先实现：

- 状态分轴和原因分类；
- 统一逆向工单、影响快照、执行任务和审计时间线；
- 商品暂停/下架/召回、退款与权益、空间回调对账三条代表链路；
- 需求聚合、商品任务关联和发布后回告；
- 运营配置版本化与回滚；
- 客户通知任务和工单关闭门槛。

生产化时再接入真实支付、财务、合同、消息、可信空间和数据资产平台接口。本地原型使用共享 mock 状态演示端到端联动，但不得用简单状态覆盖代替影响快照、处置任务和审计记录。
